## Variant C Prompt Additions (New)

**System prompt addition** (appended to `grounding_system.jinja2`):
```
11. For boolean/presence entities (gender, conditions, procedures), when the
    entity text is a simple medical concept with no numeric qualifier, always
    select the broadest matching concept code. Do not let criterion complexity
    distract from the entity being grounded.
```

**Field mapper rules addition** (appended to `operator_rules_v2`):
```
- For boolean/presence entities appearing in compound criteria joined by OR/semicolons,
  map ONLY the specific entity to relation='=', value='True'. Ignore other branches.
  Example: criterion "surgically sterile; or postmenopausal; or practicing contraception"
  with entity "Postmenopause" → relation='=', value='True', unit=null
- For ordinal scoring systems (ASA, ECOG, NYHA, etc.) with discrete listed values like
  "1, 2, or 3", use relation='=' with the enumerated values as-is. Do NOT convert to a range.
```

## Script Architecture

**New file:** `tests/e2e/run_variant_experiment.py`

Builds on patterns from `run_prompt_variants.py` and `run_grounding_snippets.py`:

### Phase 1: Cache (one-time API calls)
- `TerminologyRouter.route_entity()` per entity → candidates cache
- `normalize_unit()` per entity → unit cache (deterministic, no LLM)

### Phase 2: Run 3 Variants
For each variant (A, B, C):
1. Tag an MLFlow experiment run with `variant={name}`, `experiment_type=prompt_variant`
2. For each entity:
   - `medgemma_decide()` with variant-specific prompts → `selected_code`, `confidence`
   - `generate_field_mappings()` with variant-specific prompts → `relation`, `value`, `unit`
3. Capture per-entity trace data: latency_ms, token counts (from MedGemma + Gemini), error/retry count

### Phase 3: Score & Compare
Score each variant on 5 dimensions per entity:
- **Code match**: `selected_code == expected`
- **Relation match**: `field_mapping.relation == expected`
- **Value match**: `field_mapping.value == expected`
- **Unit UCUM match**: from `normalize_unit()` cache
- **Unit OMOP match**: from `normalize_unit()` cache

### Phase 4: MLFlow Trace Analysis
After all 3 variants complete, query the MLFlow trace store to analyze:

1. **Failure pattern clustering** — group mismatches by entity type (Condition, Procedure, Demographic, Medication, Lab_Value) and failure dimension (code/relation/value). Identifies whether failures are entity-type-specific or prompt-generic.
2. **Confidence vs accuracy** — for each variant, plot confidence scores against actual correctness. Low confidence + correct = conservative model. High confidence + wrong = dangerous hallucination. This tells us if the model "knows what it doesn't know."
3. **Retry effectiveness** — count how many entities required retries per variant and whether retries improved or degraded the outcome. High retry count with no improvement = wasted API budget.
4. **Latency breakdown** — compare median/p95 latency per variant. If variant C is significantly slower without meaningful accuracy gain, B may be preferable.

Trace data is collected inline during Phase 2 (each `medgemma_decide` and `generate_field_mappings` call already writes MLFlow spans via the existing tracing infrastructure). The script reads back trace metrics from the SQLite store at `.mlflow/mlflow.db` after all variants complete.

### Phase 5: Decision — Stop or Continue?
The script prints a recommendation based on the results:

| Outcome | Action |
|---------|--------|
| One variant scores 100% on all dimensions | **Stop.** Declare winner. Print the prompt diff to apply to production. |
| Best variant has ≤2 failures and they're in one entity type | **Stop.** Flag the specific entity type for a targeted 4th variant. Print what the 4th variant should address. |
| Best variant has >2 failures spread across types | **Continue.** Auto-generate a Variant D hypothesis from the failure pattern analysis: which prompt section to change and what the change should be. Save the hypothesis to `prompt_variant_results/variant_d_hypothesis.md`. |
| All variants perform equally (no improvement over baseline) | **Stop.** The prompts aren't the bottleneck — investigate TerminologyRouter candidate quality or model capability instead. |

## Primary Solution: Add Required Fields

The most reliable fix is to explicitly add the `required` attribute to your JSON schema, listing all field names. This prevents the model from entering repetition loops: [discuss.ai.google](https://discuss.ai.google.dev/t/model-deprecations-and-replacements-gemini-flash-2-0/109757)

```json
{
  "type": "object",
  "properties": {
    "field_1": {"type": "string"},
    "field_2": {"type": "integer"}
  },
  "required": ["field_1", "field_2"]
}
```

If using Pydantic, explicitly mark fields as required using ellipsis (`...`): [discuss.ai.google](https://discuss.ai.google.dev/t/model-deprecations-and-replacements-gemini-flash-2-0/109757)

```python
from pydantic import BaseModel, Field

class YourModel(BaseModel):
    field_1: str = Field(...)
    field_2: int = Field(...)
```
