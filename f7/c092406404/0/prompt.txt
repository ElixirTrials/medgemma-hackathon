# Plan: Fix Grounding Failures

## Context

The protocol processing pipeline (ingest→extract→parse→ground→persist) has 6 documented grounding failures that cause entities to fail terminology matching. Root causes span prompt engineering, schema validation, domain filtering, and acronym handling. This plan addresses failures #1-#6 from `instructions/SubmissionRequirements/grounding_failures/fixing_failing_groundings.md` (failure #7 is a frontend UI issue, out of scope for this backend plan).

---

## Fix 1: Over-Decomposition of Complex Concepts

**Problem**: LLM splits compound medical concepts ("tricompartmental knee replacement" → "knee replacement" + orphaned "tricompartmental"). Conversely, multi-condition phrases sent as one entity get zero matches.

**File**: `services/protocol-processor-service/src/protocol_processor/prompts/entity_decompose.jinja2`

**Changes**:
- Add explicit rules to the Jinja2 prompt:
  - "Do NOT separate anatomical modifiers, severities, or procedure types from their parent concept. Keep 'tricompartmental knee replacement', 'spinal muscular atrophy', 'non-small cell lung cancer' as single entities."
  - "DO separate distinct comorbidities into individual entities. 'Type 2 diabetes with nephropathy' → two entities: 'type 2 diabetes' AND 'nephropathy'."
  - "The `value` field is NOT used by this tool. Only extract `text` (the medical concept) and `entity_type`."
- Add concrete positive/negative examples to the prompt.

---

## Fix 2: Hallucinated Relations in Field Mappings

**Problem**: `FieldMappingItem.relation` is an unconstrained `str`. LLM generates invalid operators like "contains", "has", "is".

**File**: `services/protocol-processor-service/src/protocol_processor/tools/field_mapper.py`

**Changes**:
- Change `FieldMappingItem.relation` from `str` to `Literal["=", "!=", ">", ">=", "<", "<=", "within", "not_in_last", "contains", "not_contains"]`
- Add a `@field_validator("relation", mode="before")` that runs `_normalize_relation()` before validation, so LLM outputs like "has", "is", "==" get normalized to valid values before the `Literal` check rejects them
- This leverages Gemini's `with_structured_output` retry-on-ValidationError behavior

---

## Fix 3: Categorical Values Not Grounded to Terminology

**Problem**: Field mapping values like "Severe", "NYHA Class III", "Stage IV" are left as raw text without terminology codes.

**Files**:
- `services/protocol-processor-service/src/protocol_processor/tools/field_mapper.py`
- `services/protocol-processor-service/src/protocol_processor/nodes/ground.py`

**Changes**:
- In `field_mapper.py`, add `value_concept_id: str | None` and `value_concept_system: str | None` fields to `FieldMappingItem`
- In `ground.py` `_ground_entity_parallel()`, after generating field_mappings, add a post-processing step that:
  1. Checks each mapping's value — if it's `type="standard"` and the value text is non-numeric (regex check), attempt to ground it
  2. Uses the existing `unit_normalizer.normalize_value()` first (fast path for known categoricals like "positive"/"negative")
  3. Falls back to a lightweight `lookup_omop_concept()` call for clinical text values
  4. Populates `value_concept_id` on the mapping dict
- Guard with a try/except so failures don't block the entity grounding result

---

## Fix 4: Retry Loop Wastes Steps on Identical Queries

**Problem**: When initial grounding returns zero candidates, the agentic reasoning loop retries with near-identical queries, wasting all 3 attempts.

**Files**:
- `services/protocol-processor-service/src/protocol_processor/prompts/grounding_system.jinja2`
- `services/protocol-processor-service/src/protocol_processor/prompts/grounding_reasoning.jinja2`

**Changes to `grounding_system.jinja2`**:
- Add a "Search Strategy" section:
  - "If your first terminology search yields 0 results, DO NOT retry the exact same phrase or minor variations."
  - "Simplify to the core medical noun: 'Left ventricular hypertrophy' → 'ventricular hypertrophy' → 'hypertrophy'."
  - "Expand abbreviations: 'HTN' → 'hypertension', 'MI' → 'myocardial infarction'."

**Changes to `grounding_reasoning.jinja2`**:
- In Q3 (Rephrase), add explicit instruction: "If the previous search returned 0 results, you MUST suggest a substantially different, simpler query — not a minor variation of the same phrase."
- Add examples of good simplifications.

---

## Fix 5: Overly Restrictive OMOP Domain Filtering

**Problem**: `omop_mapper.py` filters by a single OMOP domain per entity type. "Pregnancy" (Observation) searched only in "Condition" gets zero results.

**File**: `services/protocol-processor-service/src/protocol_processor/tools/omop_mapper.py`

**Changes**:
- Replace `_get_domain_filter() -> str` with `_get_domain_filters() -> list[str]` that returns primary + fallback domains:
  ```python
  ENTITY_TYPE_TO_OMOP_DOMAINS: dict[str, list[str]] = {
      "Condition": ["Condition", "Observation"],
      "Medication": ["Drug"],
      "Lab_Value": ["Measurement", "Observation"],
      "Procedure": ["Procedure", "Observation"],
      "Demographic": ["Observation", "Measurement"],
  }
  ```
- Update `_query_concept_table()` and `_query_synonym_table()` SQL to use `domain_id IN :domains` instead of `domain_id = :domain_id`
- Update `_sync_lookup()` to pass the domain list
- Score candidates from the primary domain higher (small bonus) to prefer correct-domain matches

## Fix 6: Tools-First Acronym Resolution (Zero Extra LLM Tokens)

**Problem**: Terminology APIs don't recognize medical acronyms ("HTN", "MI", "DM", "CKD"). The TerminologyRouter sends them raw and gets zero results.

**Approach**: Use existing terminology tools (UMLS, SNOMED, OMOP concept_synonym) smarter — they already index abbreviations. Only fall back to MedGemma's agentic retry loop (Fix 4) if all tools fail. Zero additional LLM token cost.

**Files**:
- `services/protocol-processor-service/src/protocol_processor/tools/terminology_router.py`
- `services/protocol-processor-service/src/protocol_processor/tools/omop_mapper.py`
- `services/protocol-processor-service/src/protocol_processor/nodes/ground.py`

**Changes**:

1. **Add `_is_likely_acronym(text: str) -> bool` heuristic** in `terminology_router.py`:
   - Returns True if: `len(text) <= 6` AND `text.upper() == text` AND no spaces AND not a known short word (allowlist: "age", "sex", "BMI")
   - Pure string check, zero cost

2. **Smart routing for acronyms** in `terminology_router.py` `route_entity()`:
   - If `_is_likely_acronym(entity_text)`, always include `umls` in the API list regardless of entity type (UMLS has the broadest abbreviation coverage via its AUI atom-level synonyms)
   - Log: "Acronym detected — adding UMLS to routing for broader abbreviation coverage"
   - No extra LLM call — just ensures the most abbreviation-aware API is always queried

3. **Domain-free OMOP synonym search for acronyms** in `omop_mapper.py`:
   - If entity text is a likely acronym, skip the domain filter entirely in `_query_synonym_table()` (search across ALL domains)
   - The CONCEPT_SYNONYM table contains standard abbreviations — this finds them regardless of which domain the entity type maps to
   - Add `is_acronym: bool = False` parameter to `_sync_lookup()` and `lookup_omop_concept()`

4. **MedGemma as last resort** (already existing):
   - If all terminology tools return zero candidates for the acronym, the existing `_ground_entity_with_retry()` loop triggers `agentic_reasoning_loop()` (max 3 attempts)
   - The improved prompts from Fix 4 now explicitly guide MedGemma to expand abbreviations in Q3
   - This is the only point where LLM tokens are spent — and only for acronyms that ALL tools failed to resolve
